# 万象原野 · Aether Wilds

一款**浏览器端开放世界探索游戏**。整个世界由算法实时生成，没有一张贴图、没有一个模型文件——
山川、河流、森林、荒漠、雪原、宝箱、风之瞳全部是代码长出来的。

> 打开就能跑图：WASD 奔跑、空格跳跃、长按空格张开风之翼滑翔、E 交互。

---

## 一、怎么运行

游戏使用 ES Module，**必须通过本地服务器打开**（直接双击 `index.html` 浏览器会拦截模块加载）。

### 方式 1：一键启动（推荐）

双击项目根目录的 **`start-game.bat`**，浏览器会自动打开游戏。

脚本会依次尝试 Node.js → Python 来起一个本地服务器，端口 `8080`。

### 方式 2：手动启动

```bash
# 有 Node.js
node serve.mjs 8080

# 或用 Python
python -m http.server 8080 --bind 127.0.0.1
```

然后浏览器访问 <http://127.0.0.1:8080/>

### 方式 3：任意静态服务器

放进 Nginx / VSCode Live Server / `npx serve` 都能跑，纯静态无后端。

**环境要求**：支持 WebGL2 的现代浏览器（Chrome / Edge / Firefox / Safari 均可），
首次进入需等待约 1～3 秒生成世界。

## 三、世界有什么

**地理**：约 66% 陆地 / 34% 海洋的程序化大陆，包含深海、珊瑚浅滩、风起平原、
低语林地、烫金流沙、苍岩高地、云脊山脉、极寒雪原、苔沼湿地共 9 种生物群系，
以及高原台地这类适合奔跑的开阔地形。地形是**解析函数**而非网格数据，
所以理论上可以朝任意方向一直跑下去，世界没有边界。

**昼夜**：8 分钟一个完整昼夜（可调），太阳/月亮位置、天空渐变、雾色、
云层染色、星空、水面色泽全部随时间连续变化。

**交互物**：
- 🟡 **宝箱** —— 开启获得原石与摩拉，积累经验
- 🟢 **风之瞳** —— 悬浮的收集物，收集后获得经验与粒子反馈
- 🔵 **传送锚点** —— 激活后可在世界地图上点击传送
- 🔥 **篝火** —— 靠近交互可回满体力与生命

**成长**：收集获得经验，升级提升体力上限。

**存档**：自动写入浏览器本地存储（每 25 秒 + 暂停 + 关闭页面时），
保存位置、进度、已收集 / 已解锁标记、游戏时间。

## 四、技术实现

| 模块 | 说明 |
| --- | --- |
| `js/noise.js` | 自研 Simplex 噪声 + fBm / 山脊噪声 / 域扭曲，确定性可复现 |
| `js/terrain.js` | 高度场、坡度、气候、9 种群系判定与地表配色 |
| `js/world.js` | 分块流式加载（地形块 + 3×3 块的资源区域），按距离分级减配 |
| `js/props.js` | 全程序化低多边形植被几何体（松/阔叶/棕榈/仙人掌/岩石/草/花/芦苇） |
| `js/player.js` | 角色物理与状态机（idle/run/sprint/jump/fall/glide/swim/slide）+ 两段式四肢程序化动画 |
| `js/camera.js` | 第三人称跟随相机，0.35m 步进的地形/植被双重避障、贴脸自动隐藏角色 |
| `js/sky.js` | 天空穹顶着色器、日月光照、星空、云层、昼夜关键帧插值 |
| `js/water.js` | 波浪 + 菲涅尔 + 高光的自定义水面着色器 |
| `js/objects.js` | 交互地标，静态部件合并网格 + 共享材质以压低 draw call |
| `js/ui.js` | HUD、小地图（实时采样地形）、世界地图、菜单与设置 |
| `js/audio.js` | 纯 WebAudio 程序化音效与环境音，零音频素材 |

**性能取向**：中画质下实测约 **168 个 draw call / 27 万三角面**，
每帧游戏逻辑耗时约 **1.2～1.8 毫秒**（世界流式加载稳定后接近 0.1 毫秒/帧）。

关键优化：
- 地形顶点只做 1 次高度采样，坡度由已生成的高度网格差分得到（省掉 4/5 的噪声求值）
- 气候场（温度 / 湿度）是低频信号，改为稀疏控制点采样 + 双线性插值
- 植被按距离分级：近处完整密度，远处降到 55% 采样密度且不生成小型装饰物
- 静态部件合并网格 + 共享材质（交互物件的 draw call 降低约 60%）
- 世界加载按帧率自适应分配时间预算，帧率越低单帧预算越小，保证操作手感

## 七、开发笔记

- 地形高度是解析函数 `Terrain.height(x, z)`，小地图、世界地图、生物群系判定
  都直接采样它，因此不存在"碰撞体不同步"的问题。
- **但"贴地"必须用 `Terrain.meshHeight(x, z)`，不能用 `height()`。**
  网格步长只有 `64/段数 ≈ 2.29` 米（中画质），采不出高度场里 7～20 米波长的细节，
  两者在起伏处最多差 2～3 米。凡是**站在地面上**的东西（角色、相机、植被、石头、
  传送落点、地标选址）都走 `meshHeight`，这样"脚踩的"和"看到的"永远是同一个面。
  它必须与 `world.js` 的三角剖分约定（`fx + fz = 1`）保持一致，改一处要改两处。
- 台地整形之类的"风格化"处理**必须是连续函数**。用 `Math.round` 这类阶跃函数
  会在网格步长的尺度上造出画不出来的垂直断崖，表现就是角色悬空。
- 地形分块的顶点坐标由世界坐标推导，相邻块共享同一条采样线，
  因此不同精度之间也不会出现裂缝。
- 相机避障按 **0.35 米**逐点步进扫描镜头到角色的连线：撞到地形就把镜头拉到
  碰点前 0.55 米，撞到植被遮挡体（树干 / 巨石圆柱）拉到前 0.5 米，
  最后再对相机高度做一次"不低于地面 +0.75 米"的硬约束。
- **探测上限必须用 `targetDistance`（玩家设定的目标距离），不能用当前 `distance`**：
  否则会形成单向棘轮 —— 被地形压近过一次之后，探测上限也跟着变小，
  镜头就永远拉不回来了。
- 被土坡顶住时不要硬挤到角色脸上，而是**逐级抬高俯仰角换一个俯视机位**；
  只要能看到角色就停止抬高。这样镜头不会贴脸，角色也不会被挤到占满画面。
- 相机位置做了平滑，所以**平滑之后还要再夹一次**地面高度（+0.6 米），
  并沿"角色 → 平滑后位置"的真实连线再检查一次遮挡：
  只约束"目标位置"是不够的，快速甩镜头时滞后会让视线穿过山体。
  镜头贴到 1.8 米内不再隐藏角色（只有第一人称才隐藏）。
- 角色无法继续攀爬时不会硬性清零速度，而是把本帧位移按可通行比例衰减，
  并沿坡面法线施加下滑加速度（`slideAccel = 15`），
  所以陡坡上表现为"滑下去"而不是"卡住"。
- 植被在坡面上的朝向按地形法线做 55% 混合，避免树木直直插在斜坡上产生的穿模感。
- 所有资源加载都有时间预算（默认每帧 6.5ms），边跑边加载不会卡顿。

## 八、修复记录

针对实测反馈的四个问题（穿模 / 卡在山体里 / W-S 方向反 / 建模粗糙）的修复与验证：

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 游戏穿模 | ① 相机步进从 2.5 米才开始检测，可钻进地形；② 地面硬约束只加在"目标位置"上，平滑滞后会让镜头短暂陷进山体；③ 树木在斜坡上始终竖直生长 | ① 改为 0.35 米密集步进 + 地形硬下限；② 平滑之后**再夹一次**地面高度；③ 植被按地形法线 55% 混合对齐 |
| 2 | 人物卡在山体里 | 爬坡超过阈值时速度被砍到 0.05，等于原地不动 | 改为按可通行比例衰减位移 + 沿坡面法线下滑，新增 `slide`（坡面滑落）状态 |
| 3 | W 往后走 / S 往前走 | `cameraRig.yaw` 表示"由角色指向相机"的方向，取反才是镜头前方 | 前进方向改为 `(-sin yaw, -cos yaw)`，左右同理 |
| 4 | 建模粗糙 | 披风是一块 0.46×1.0 的纯平面；发型的球冠是全方位的，把整张脸都盖住了 | 披风改为椭圆截面的弧形壳体（顶点动画）；发型拆成颅顶发 + 后脑侧发，正面留出面部开口 |

自动化验证脚本 `_test/verify.mjs`（Playwright + 无头 Chromium）逐项实测：

- **W/S/D/A 方向**：按 W 后位移与"镜头前方"的方向余弦 `+1.00`，S 为 `-1.00`，
  D/A 对"镜头右侧"分别为 `+1.00 / -1.00` —— 四个方向全部正确
- **防卡住**：把角色丢到坡度 `1.00`（最陡）的云脊山脉顶峰，
  每秒把镜头对准上坡方向、持续顶坡 12 秒，逐帧统计位移 ——
  最长连续停滞 **1 帧**（仅起步加速那一帧），角色最终从山顶滑落到风起平原，
  不存在"陷进山里动不了"
- **穿模**：挂钩 `renderer.render` 逐帧用**射线检测真实地形网格**，
  检查"角色 → 相机"连线上是否被地形挡住 —— **0 帧**；
  角色陷入地形 **0 帧**；相机离地最低 **1.06 米**
- **运行时报错**：**0 条**

> 注：无头 Chromium 走的是 SwiftShader 软件光栅化，帧率只有个位数，
> 因此**不能用它的 FPS 评估真实性能**；上面的判定标准（方向余弦、逐帧位移、
> 射线命中）都刻意做成了不依赖帧率的形式。

`_test/model-shot.mjs` 则用"摄影棚模式"（暂停物理、隐藏除角色外的一切、纯色背景）
渲染角色的正面 / 侧面 / 背面 / 四分之三 / 跑动 / 滑翔特写，用来逐个排查建模问题。

## 九、第二轮修复（试玩反馈）

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 5 | 人物显示不出来 | **两个 bug 叠加**：① 镜头避障的探测上限用的是**当前**距离 `this.distance`，形成"单向棘轮"——被地形压近一次后探测上限也跟着变小，镜头就再也拉不回来，最终永久停在 1.5 米；② `main.js` 又在 `distance < 1.8` 时直接隐藏角色 | ① 探测上限改用 `targetDistance`，镜头能自动拉回；② 被挡时不再硬挤贴脸，改为**逐级抬高机位走俯视**；③ 隐藏条件放宽到 `< 0.9`，第三人称不再因为靠近而消失 |

- **贴脸场景**（背后 5.5 米内地形抬高 20 米以上）：角色被隐藏的帧 **19/20 → 0/19**；
  镜头距离从"卡死在 1.5 米"变成在 1.5～3.2 米之间自适应

- **视线遮挡**：快速甩镜头时"角色被地形挡住"的帧 **8/45 → 0/36**
- 第一阶段的四项回归（方向 / 防卡 / 穿模 / 报错）全部保持通过

## 十、第三轮修复（岩石"碎成一堆三角板"）

试玩反馈："在云脊山脉山顶，画面被大片深色平板糊住了，这个建模对吗？"

结论：**不对，而且是一个可以精确复现的几何缺陷**。

### 根因：非索引几何 + 按顶点下标播种的随机扰动

`three.js` 的多面体几何（`IcosahedronGeometry` / `PolyhedronGeometry`）是**非索引**的：
一个二十面体有 12 个空间顶点，但 `position` 属性里存了 **60 个顶点**——
每个顶点被相邻的 5 个三角面各复制了一份。

而 `props.js` 里的岩石扰动是这么写的：

```js
// ❌ 修复前
for (let v = 0; v < pos.count; v++) {
  const k = 0.62 + (Math.sin(v * 31.3 + i * 7.1) * 0.5 + 0.5) * 0.7;  // 种子 = 顶点下标 v
  pos.setXYZ(v, pos.getX(v) * k, pos.getY(v) * k * 0.7, pos.getZ(v) * k);
}
```

同一个空间位置的 5 份副本拿到了 **5 个不同的 `k`**，于是被推向 5 个不同方向 →
公共边被撕开，岩石碎成一堆互相分离、悬在空中的大三角板。

用"边界边计数"量化（封闭流形的每条边都应恰好被 2 个三角面共用）：

| 几何体 | 三角面 | 边界边（修复前） | 最长裂缝 |
| --- | --- | --- | --- |
| `rock`（size 1.15） | 120 | **180 / 180 条边全是裂缝** | 2.13 m |
| `boulder`（size 2.6） | 300 | **720** | 2.96 m |

超过 `size` 一半的撕裂量——所以看起来就是"一堆飘着的平板"，完全对得上试玩截图。

**修复**：新增 `jitterRadial(geo, kMin, kMax, squashY, seed)`，
用顶点的**空间方向**（`normalize(x,y,z)`，同一位置的所有副本完全相同）
而不是下标当随机种子；每块石头用不同的 `seed` 保证形状各异，但同一块石头内部种子恒定 → 不撕开。
修复后边界边 **180 → 0**、**720 → 0**，几何体完全封闭。

顺带修掉 `objects.js:buildFireGeo`（篝火围石）里一模一样的写法。

## 十一、第四轮修复（角色走路"悬空"）

试玩反馈："在烫金流沙上正常走路，人物是悬空的，影子落在脚下方很远的地方。"

这是一条**数值可精确复现**的反馈。先说结论：

> 角色脚下踩的高度和眼睛看到的地面**不是同一个东西**。
> 前者是解析函数 `height(x, z)` 的值，后者是地形网格三角面插值出来的值，
> 两者在起伏处最多差 **2～3 米**。

### 根因 A：台地整形用了阶跃函数

`terrain.js` 里为了让某些区域更平坦开阔，加了一层"高原台地"整形：

```js
// ❌ 修复前
const plateau = smoothstep(0.52, 0.84, this.nCave.fbm(...) * 0.5 + 0.5);
const terrace = Math.round(h / 8) * 8;          // ← 阶跃！
h = lerp(h, terrace, plateau * 0.6 * continent);
```

`Math.round(h / 8) * 8` 是一个**阶跃函数**：`h` 一旦跨过 `8k + 4`，
取整结果就**整体跳 8 米**；按 `0.6` 的混合权重算，就是高度场**瞬间跳 4.8 米**。

而地形网格的细分步长只有 `64 / 28 ≈ 2.29` 米 —— 网格画不出这种垂直断崖，
只能把它拉成一条 2.29 米宽的陡坡。于是"角色站在解析高度上、眼睛看到的是网格高度"，
两者在这道坡上最多差 3～4 米 → 角色悬空或陷进沙里。

修复：改用 `smoothstep` 过渡的**软阶梯**（约 2/3 的高度区间仍是平的，台地感保留），
但高度场处处连续，网格能忠实还原：

```js
// ✅ 修复后
const cell = h / 8;
const base = Math.floor(cell);
const terrace = (base + smoothstep(0.34, 0.66, cell - base)) * 8;
h = lerp(h, terrace, plateau * 0.6 * continent);
```

### 根因 B（决定性）：地形细节比网格还细

把阶跃改连续之后**问题依然存在**。因为 `height()` 里含有 **7～20 米波长**的细节，
而网格步长只有 2.29 米 —— 采样不足，画出来的面必然偏离解析值。

实测（`_test/diag-height.mjs`，用"网格中点插值误差"衡量，
即解析高度与网格三角形中点高度的偏差）：

| 检查方式 | 修复前 | 修复后 |
| --- | --- | --- |
| 网格中点插值误差（基础地形，无台地） | **1.88 ～ 2.16 m** | 0.00 m |
| 网格中点插值误差（含台地整形） | **5.15 m** | 0.00 m |

**所以这不是调参能解决的**：只要角色还贴 `height()`，就一定会浮。
必须让角色站在**画出来的那个面**上。

### 修复方案：`Terrain.meshHeight()`

新增一个与地形网格**逐点完全一致**的高度函数：顶点取解析高度，
三角形内部做线性插值，并且**必须沿用 world.js 建网格时的同一套三角剖分**。

```js
/** 地形网格默认步长（米）：64 米的地形块 ÷ "中"画质的 28 段。World 会按画质覆盖它 */
export const DEFAULT_MESH_STEP = 64 / 28;

meshHeight(x, z, step = this.meshStep) {
  const i = Math.floor(x / step), j = Math.floor(z / step);
  const x0 = i * step, z0 = j * step;
  const fx = (x - x0) / step, fz = (z - z0) / step;
  const h00 = this.height(x0, z0);
  const h10 = this.height(x0 + step, z0);
  const h01 = this.height(x0, z0 + step);
  const h11 = this.height(x0 + step, z0 + step);
  if (fx + fz <= 1) {
    return h00 + fx * (h10 - h00) + fz * (h01 - h00);           // 三角 a-c-b
  }
  return h11 + (1 - fx) * (h01 - h11) + (1 - fz) * (h10 - h11); // 三角 b-c-d
}
```

> ⚠️ **剖分约定必须锁死**。`world.js` 里建面用的是
> `indices.push(a, c, b, b, c, d)`，等价于对角线 `fx + fz = 1`。
> 如果哪天改了这行，`meshHeight` 也必须跟着改，否则又会错开。

网格步长由 `World` 按画质写入，切画质时会同步更新：

```js
this.terrain.meshStep = CHUNK_SIZE / this.segments;   // 构造函数 + setQuality()
```

然后把**所有"站在地面上"的调用点**从 `height()` 换成 `meshHeight()`：

| 文件 | 位置 | 数量 |
| --- | --- | --- |
| `player.js` | 出生落地 / 生物群系判定 / 越障判定 / 贴地吸附 | 4 |
| `camera.js` | 镜头避障与地面硬约束 | 4 |
| `main.js` | 出生点 / 传送落点 / 坠落救援 | 3 |
| `world.js` | 植被石头散布高度 / 地标选址 | 2 |

**保留 `height()` 的地方**（这些本来就该用解析值）：
地形网格顶点高度、生物群系与海平面判定、坡面法线 —— 它们要么是网格的输入，
要么只需要"大致在哪"。

### 排查方法沉淀

1. **冻结相机的 A/B 对照**：先把相机位姿存下来、暂停物理、再原样恢复相机，
   只改"角色落地高度"这一个变量 —— 两张图除角色外完全重合，
   这样"悬空"就不再是主观观感，而是一个可以量化的高度差。
2. **不要用连续性判据测阶跃**：最初用 `|h(x+ε) − h(x−ε)|` 衡量连续性，
   修复前也几乎为 0 —— 因为 `Math.round` 的跳变是**零宽度**的，探针直接跨过去了。
   换成"网格中点插值误差"才正确地把问题放大到 5.15 m。
3. **基准要选对**：任何"物体贴地"的检查，基准都必须是**渲染出来的面**，
   而不是那个被采样的连续函数 —— 两者在采样不足时必然分家。
4. **小心 DOM 覆盖层**：排查画面上的小白点时，射线检测、隐藏 3D 对象、
   甚至把整个 `scene` 清空都消不掉它 —— 因为它是 HTML 元素（本作的**准星**：
   `#crosshair` 里一个 4×4 的白点，固定屏幕中心）。
   踩的坑：`document.elementsFromPoint()` **会跳过 `pointer-events: none` 的元素**，
   而准星恰好就是 `pointer-events: none`，所以查不到。
   正确做法是遍历所有元素、自己判断 `getBoundingClientRect()` 是否包含该点。
   **凡是"固定在同一屏幕位置、换镜头也不动"的疑似渲染瑕疵，优先怀疑 DOM。**

## 十三、第六轮修复（世界地图分辨率 / 页面尺寸）

试玩反馈两条：

> 1、这个地图分辨率有点低，提高分辨率　2、点击 M 键后，展示的地图比较小，把地图页面扩大

### 1. 先把"提高多少"变成一个数字

提高采样分辨率是有代价的：地形高度是纯 JS 噪声求值，GPU 帮不上忙，
采样点数按 **平方** 增长。所以先用 `_test/bench-map.mjs` 把代价曲线量出来，
而不是拍脑袋写个 1024：

| 采样分辨率 | 只采样高度 | 含地表配色 |
| --- | --- | --- |
| 128×128 | 23.6 ms | 23.6 ms |
| 256×256 | 60.0 ms | 70.4 ms |
| 384×384 | 133.9 ms | 162.1 ms |
| **512×512** | **228.6 ms** | **272.3 ms** |
| 640×640 | 360.4 ms | 414.4 ms |

- 128 → 512 是 **4 倍线性、16 倍像素**，耗时从 24 ms 涨到 272 ms；
- 512 以上收益递减而代价陡增，640 已经接近半秒；
- 世界地图是**一次生成、静止不动**的（打开地图时世界暂停），
  所以几百毫秒的一次性开销是可以接受的 —— 但**不能卡在点击回调里同步跑**。

最终 `bmSamples = 512`。浏览器里实测（Chromium 无头）：128 → 88 ms，
512 → 415 ms（无头软件渲染偏慢，真机更快）。

**配套改动**：`toggleMap(true)` 不再同步渲染，先画一个轻量占位
（`placeholderBigMap()`，深色底 + "正在生成地图…"），把面板先送上去，
再在**下一帧**用 `requestAnimationFrame` 生成真正的地图。
否则玩家会觉得"按了 M 愣半秒才弹出来"。

### 2. canvas 内部分辨率应该跟着显示尺寸走

原来的 canvas 固定 `width=1024`，而 CSS 宽度由 `min(66vh, 600px)` 决定 ——
两者毫无关系：窗口小就白白多算像素，窗口大就发虚。

新增 `_sizeBigmap()`：每次渲染前按 `显示宽度 × DPR`（钳制在 512…1600）重设
canvas 尺寸，并且让 `#bigmap` 直接撑满视口：

```css
#bigmap {
  width:  min(calc(100vh - 126px), calc(97vw - 36px), 980px);
  height: min(calc(100vh - 126px), calc(97vw - 36px), 980px);
}
```

`126px` = 卡片上下 padding(24) + 标题行(~30) + 两处 gap(18) + 图例(~20) + 余量。
在 1440×900 下地图从 **594px → 774px**，卡片高 863 / 视口 900；另加了
`@media (max-height: 700px)` 让矮屏也不溢出（700×520 实测卡片 495 高，不溢出）。

> **两点要说明白**（避免误解 `_sizeBigmap` 的钳制值）：
> - 画布上限 `1600` 只是为了防止极端窗口下白算，**真正决定地图清晰度的是
>   `bmSamples = 512` 那份地形缓冲**。canvas 只是把它放大显示（用
>   `imageSmoothingQuality = 'high'`），所以画布开到 874 或 1548，
>   地形细节的上限都是 512×512。
> - 换句话说：**标记和文字的锐利度** 跟随 canvas 分辨率（所以 DPR=2 时更锐），
>   **地形的锐利度** 跟随 `bmSamples`。两者是分开的，想再提地形细节只能调 `bmSamples`，
>   而那要按平方付代价（见 §1 的表）。512 是"细节够用 / 耗时可控"的折中点。

### 3. ⚠️ 最容易被忽略的一步：所有绘制尺寸都要乘 `U`

canvas 分辨率一提高，**如果还按画布像素写尺寸，标记和文字会同比缩成小点**。
所以引入一个换算因子：

```js
const U = S / (this.el.bigmap.getBoundingClientRect().width || S);
// U ≡ DPR。之后所有尺寸都写成 "CSS 像素 × U"
```

标记半径、虚线间隔、玩家三角、比例尺文字、以及点击命中半径 `_wayHitR`
全部改成 CSS 像素语义。这样"换分辨率 / 换窗口 / 换 DPR"，标记在屏幕上看起来一样大。

这条用**两个页面**验证最直接：同一台机器上开一个 DPR=1、一个 DPR=2 的页面，
量玩家红色三角在画布上的跨度：

```
DPR 1  显示 774px  画布  774px  三角 6 画布像素 ≈ 6 CSS 像素
DPR 2  显示 774px  画布 1548px  三角 12 画布像素 ≈ 6 CSS 像素
画布像素跨度比 = 2.00（DPR 比 = 2.00）
```

> 注意：想测 `U` 的变化必须改 **DPR**，不能改 CSS 尺寸。
> 因为 `U = 画布宽 ÷ CSS 宽` 而画布宽又是从 CSS 宽算出来的，
> 在 DPR 固定时 `U` 恒等于 DPR —— 改 CSS 尺寸只会让画布和 CSS 同步变大，
> 量出来的画布像素跨度**不会变**，看起来像"缩放没生效"。

### 4. ⚠️ 山体阴影的求坡基线要按世界距离固定

提高分辨率之后地图一度变得像**满屏砂纸**。原因不是分辨率，而是阴影的写法：

```js
// 旧：拿"相邻一个像素"求坡
const hR = hs[i + 1];
const shade = 1 + (h - hR) * gx;        // gx = 0.045
```

地形是分形的 —— **采样越密，相邻像素的高差虽然变小，但换算成坡度反而更陡**。
把系数按"每像素多少米"归一化之后，数学上确实等价于原来 128 分辨率的观感，
但那只对"同一条坡"成立；细分之后多出来的那些高频起伏，本身坡度就更大，
于是阴影被放大成噪声。实测相邻像素阴影差的中位数占到整个值域的 **20%**。

改成**固定按约 17.3 米的间隔求坡**（也就是 128 分辨率时代的基线）：

```js
const kShade = Math.max(1, Math.round(17.3 / step));      // 512 时 = 4 个像素
const hR = k < N - kShade ? hs[i + kShade] : h;
const gx = 0.045 * 17.3 / (kShade * step);                // 归一到 17.3 米基准
```

代价是 0（只是换个下标），换来的效果是：**海岸线 / 地表配色拿到 512 的全部细节，
而浮雕质感保持原来的柔和度**。

### 5. 顺带确认：地图上的"同心圆纹理"不是 bug

地图上有大量同心环状纹理，看着像渲染瑕疵，所以做了分层诊断
（`_test/diag-map-rings.mjs`）：在同一位置、同一 512 网格上，把
**纯高度 / 纯配色 / 纯阴影**分别导出成三张图。

结论：**配色层就已经有那些环** ⇒ 纹理来自高度场本身（大陆性与丘陵噪声在
2.2 km 窗口内的正常形态），不是新引入的。顺带量到：
高度范围 −15.4 → 58.9 m，海洋占 34%，相邻像素高差均值 1.68 m / 最大 40.8 m。
